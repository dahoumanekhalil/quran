# ADR-0008: Hilt for dependency injection

- **Status:** Accepted
- **Date:** 2026-09-04
- **Deciders:** dahoumanekhalil
- **Review date:** before Phase 5

## Context and problem statement

The app needs to wire ViewModels, repositories, and data sources across ~10 modules. DI keeps modules loosely coupled and testable.

## Decision drivers

- Compile-time safety (fail at build, not at runtime, when a dep is missing).
- ViewModel scoping and lifecycle awareness.
- Multi-module ergonomics (see ADR-0019).
- Small learning curve, wide community.
- Charter #13 — dependencies chosen carefully.

## Options considered

### Option A — Hilt

Google's Dagger-based DI framework for Android. Compile-time verified, `@HiltViewModel` integration with `viewModel()` composables, first-class Room / DataStore examples. Standard for new Android apps.

### Option B — Koin

Kotlin-only, service locator style, runtime resolution. Simpler to set up, but errors are runtime (violates "correctness beats cleverness"). Weaker multi-module story.

### Option C — Manual DI (constructor injection with a single `AppContainer`)

Zero dependencies. For a 3-module app this is fine; for our ~10 modules it becomes a bookkeeping burden.

## Decision

**Hilt (Option A).**

Compile-time safety and ViewModel integration outweigh the extra build-time cost. The learning curve is modest and the patterns are well documented.

## Consequences

- Positive: safe wiring, `@HiltViewModel` works with Compose, `@InstallIn(SingletonComponent::class)` scopes are explicit, easy to swap fakes in tests.
- Negative: annotation processing adds compile time; KSP now supported (as of Hilt 2.48+). Adds ~1 MB to the APK.
- Follow-up: TASK-030 sets up Hilt in the initial Gradle config with KSP.
