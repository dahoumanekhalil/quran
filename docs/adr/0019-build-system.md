# ADR-0019: Gradle Kotlin DSL + version catalog + multi-module structure

- **Status:** Accepted
- **Date:** 2026-09-04
- **Deciders:** dahoumanekhalil
- **Review date:** before Phase 3

## Context and problem statement

The Android app needs a build system, a version-management approach, and a module topology. All three are hard to change once the codebase grows.

## Decision drivers

- Type-safe build scripts.
- Single source of truth for dependency versions.
- Module boundaries that align with the architectural layers (ADR-0004, ADR-0010, ADR-0011, ADR-0012) so violations are compile errors.
- Compatible with cloud CI (ADR-0023).

## Options considered

### Build script language

- **Kotlin DSL (`build.gradle.kts`)** (recommended) — type-safe, IDE-friendly, aligns with ADR-0001.
- Groovy DSL (`build.gradle`) — legacy default; less type-safe.

### Version management

- **Version catalog (`gradle/libs.versions.toml`)** (recommended) — single file with `libs.androidx.compose.bom`, `libs.hilt`, etc. Type-safe accessor generated by Gradle.
- Hard-coded versions per module — error-prone drift.
- `buildSrc` — pre-catalog pattern, more code.

### Module topology

- **Multi-module by architectural layer** (recommended):
  - `:app` — assembly, DI graph, `Application` class, launcher activity.
  - `:core:designsystem` — theme, typography, colors, spacing, iconography.
  - `:core:common` — utilities, extensions, common types.
  - `:core:database` — Quran DB accessor + Room + migrations.
  - `:core:datastore` — DataStore Preferences wrappers.
  - `:core:data` — repositories, data sources (internal).
  - `:core:domain` — entities, repository interfaces, thin services.
  - `:feature:reader` — Mushaf page reader.
  - `:feature:navigation` — surah / juz / page navigation.
  - `:feature:bookmarks`
  - `:feature:search`
  - `:feature:settings`
- Single module — faster initial builds, but forbidden layer imports become style violations, not compile errors.

## Decision

**Kotlin DSL + version catalog + multi-module structure as above.**

Module dependency direction: `:app` → `:feature:*` → `:core:*`. No `:feature:X` depends on `:feature:Y`; cross-feature integration goes through `:app` (deep links + navigation graph).

## Consequences

- Positive: layer violations become compile errors; version drift eliminated; type-safe scripts; matches Google's `nowinandroid` reference structure.
- Negative: more modules = more Gradle configuration overhead; mitigated by convention plugins in `build-logic/` if configuration duplication becomes painful.
- Follow-up: TASK-031 (Phase 3) defines the module graph and sets up the version catalog; TASK-033 (Phase 3) adds convention plugins if needed.
